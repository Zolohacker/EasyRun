# 客户端版本门禁与平台更新

## 两套版本相互独立

管理后台 **运行总览** 的版本卡片分别展示：

1. **闪动校园客户端版本**：检查当前已适配版本是否仍被服务端接受。
2. **EasyRun 平台版本**：从固定仓库 `Zolohacker/EasyRun` 的稳定 GitHub Release 检查及安装平台程序。

客户端发布新 APK 不会让平台自动获得新协议适配。强更后需要发布已适配的平台版本，重新检查通过后才恢复跑步任务；没有“忽略强更”的开关。

## 客户端检查更新

- 使用已适配 Android `8.7.9` / Build `26101910` 的 `POST /run-front/common/update`，复用协议客户端公共参数；不使用任何客户的登录凭据。
- 接口来源：客户端 `BaseApi.l()`、`CommonApi.v()`，返回模型 `VersionUpgrade` 与 `VersionUpgradeDialog`。
- 读取 `haveUpdate`、`forceUpdate`、`newVersion`、`supportVersion`、更新标题及说明。
- 真实无更新响应会省略 `forceUpdate`、版本号为空。只有明确 `haveUpdate=false` 时才把省略的强更标志解释为 false，并展示“当前渠道可用版本”为当前适配版本；不宣称其他渠道版本已验证。
- 启动及每 **5 分钟**检查，可在总览手动检查（每分钟一次）。结果持久化，重启后仍保留强更状态。
- 首次未成功核实、响应格式异常且没有有效缓存、缓存超过 **10 分钟**时，服务端关闭执行门禁。短暂网络失败保留已核实结果；错误不会清除已经确认的强更标记。
- `forceUpdate=true`：拒绝手动触发和定时执行，队列中任务在执行前跳过并写明原因；已经执行的跑步任务会收到取消信号，停止后续请求。定时到期的受阻任务记录为跳过，恢复后不集中补跑。
- 门禁在调度器和最终提交入口双重检查，不依赖浏览器按钮。强更检查不会阻止后台查看账号、记录、修复配置或更新平台。

## 平台自动更新

设计参考 [sub2api 的更新服务](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/update_service.go)，本项目独立实现，并增加 Windows 独立守护进程、ZIP 安装和启动身份验收。

- 每 **20 分钟**检查稳定 Release，跳过草稿与预发布；提供手动检查、一键更新及上一版回滚。
- **闲时自动安装默认关闭**，超管可在版本卡片设置中开启。必须没有正在执行及排队的任务，钱包后台事务也须空闲；准备更新时暂停新任务和归集，已持久化的充值检查保留至重启恢复。更新不会为安装而中断正在运行的任务或钱包事务。
- 固定来源、固定 OS/架构安装包名、GitHub 下载域名白名单，跨域重定向移除 Token。
- 必须有匹配的 `checksums.txt` 与 SHA-256，禁止路径穿越、链接、重复程序及超限压缩包。
- 先运行候选程序 `--version-json` 验证版本、系统、架构与本地推理支持，探测进程不继承数据库、主密钥及钱包凭据。
- 独立守护进程在服务器退出后替换程序，保留上一版备份；新版本在 **60 秒**内通过本机数据库健康检查、版本/提交号、随机启动标识的共同验收后才放行任务。原已就绪的人脸推理也须保持就绪，失败自动恢复原二进制。
- 同一失败发行版不会被闲时自动安装无限重试；主动回滚后也不会立即自动重装刚撤回的版本，超管可手动重试或等待后续新版本。只有上一份完整二进制备份可回滚。
- 更新只替换平台二进制与内嵌前端，不替换 `.env.local`、数据库、钱包、模型及资源文件；外部 DLL/SO、模型文件的更新需单独部署。

### 公开更新源

固定从公开仓库获取稳定发行版，免填访问凭据；前端、API 和下载器不再提供私有仓库凭据设置。旧部署历史凭据自动清空，不复用开发机登录状态。公开下载行为见 [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)。

没有 Release 或网络异常时明确显示“更新源待就绪”，而不是错误地显示已经是最新版。安装、回滚和修改闲时自动安装设置仅超级管理员可操作，并需再次验证密码。

### 启动方式

**Windows 本地**：

```powershell
.\scripts\start-local.ps1
```

脚本复制 `bin/easyrun.exe` 为独立的 `bin/easyrun-supervisor.exe`，后者使用 `--supervise` 启动真正的服务器。直接运行服务器仍可检查版本，但在线安装按钮保持禁用并提示使用守护模式。

**Linux 二进制部署**：在程序停止时准备独立守护副本：

```bash
cp /opt/easyrun/bin/easyrun /opt/easyrun/bin/easyrun-supervisor
chmod 755 /opt/easyrun/bin/easyrun{,-supervisor}
# 在原有配置/模型路径对应的工作目录中启动，环境保持不变：
/opt/easyrun/bin/easyrun-supervisor --supervise /opt/easyrun/bin/easyrun
```

systemd 使用独立守护副本作为 `ExecStart`，设置正确的 `WorkingDirectory`、原有 `EnvironmentFile`，建议 `Restart=always`。运行用户需能写程序目录与其下 `.easyrun-update`。健康检查要求 HTTP 绑定回环地址或通配地址，例如 `HTTP_ADDR=:8080`。

**新版容器部署**：支持在运行总览一键更新平台程序、闲时自动安装及回滚。镜像内的 `/usr/local/bin/easyrun --container-supervise` 作为独立守护进程，将可替换的应用放在 `/app/runtime/easyrun`；Compose 默认挂载独立的 `easyrun_runtime` 命名卷。容器继续使用 UID `10001` 的普通用户，不挂载 Docker socket、不申请特权模式，也不修改镜像内的原始程序。

- 首次启动初始化程序卷；同一镜像重启或重新创建容器时，保留已在线安装的版本和更新恢复状态。数据卷的生命周期独立于容器，使用说明见 [Docker Volumes](https://docs.docker.com/engine/storage/volumes/)。
- 超管在「运行总览 → 平台更新」操作，只有任务和钱包事务空闲时执行。更新失败会恢复原程序，过程与二进制部署共用校验及验收逻辑。
- 程序卷使用进程级独占锁，重复挂载给同时运行的第二个实例会停止该实例启动，避免互相替换程序。
- 容器停止时守护进程向应用转发 `SIGTERM`，等待请求收尾后退出；Compose 预留 `30s` 停机宽限期。
- 候选程序必须支持相同的容器守护协议。基础镜像、系统依赖、原生库或模型文件变化时，仍应重建镜像；网页更新只替换平台主程序及内嵌前端。
- 显式部署不同的镜像程序时，以新镜像自带程序为准，旧更新状态移动到程序卷内的 `.easyrun-update-archived-*` 目录留存，不沿用跨镜像的待执行更新或回滚元数据。此规则也适用于主动部署旧镜像；数据库与主密钥保持不变，仍需关注数据库迁移兼容性。

### 目录权限与容器更新

`v0.1.3` 起，更新器分别检查**程序所在目录**和同级 **`.easyrun-update` 暂存目录**，显示具体路径及操作系统错误。修复后刷新版本卡片或点击「检查更新」即可重新检测，不再永久保留启动时的权限失败结果。检测只创建并删除独立临时文件，不写入正在运行的程序，也不会自动更改目录权限。

**二进制部署**：确认服务运行账号，而不是浏览器登录账号，具有上述两个目录的创建、写入及删除权限。同名普通文件占用 `.easyrun-update` 路径时，应先核对该文件用途并处理路径冲突，不要直接删除未知文件。仍需使用独立守护副本启动，且程序替换时服务与钱包事务空闲。

- Linux：检查服务配置中的 `User` / `Group`、安装目录归属及挂载是否只读，给实际服务账号授予对应安装目录权限，不要对整个系统目录递归放宽权限。
- Windows：检查实际服务运行账号对安装目录的「修改」权限。运行中的 EXE 被系统锁定是正常行为，更新器应由独立守护副本在进程退出后替换它。
- `v0.1.2` 及更早版本会缓存启动时的失败结果：首次升级到修复版本前，修复权限后重启旧服务再更新，或在空闲时手动替换发行包中的主程序。

**从旧容器迁移（仅首次需要）**：旧版本尚未使用独立程序卷，先更新启动方式和卷配置。使用本仓库 `compose.yaml` 源码构建方式的部署，在确认任务与钱包事务空闲、完成备份后，在宿主机项目目录执行：

```bash
git pull --ff-only
docker compose build --pull app
docker compose up -d --no-deps app
```

上述命令重建应用服务，沿用原有 `.env`、数据库卷和主密钥卷，新增程序卷；不要执行 `docker compose down -v`。迁移后版本卡片应显示「容器内持久化更新」，之后安装兼容的平台发行版可直接使用网页的一键更新。基础镜像更新继续使用上述宿主机命令。

如果使用自定义 Compose 或部署面板，请保留镜像默认命令 `--container-supervise`，设置 `EASYRUN_RUNTIME_DIR=/app/runtime`，将独立持久卷挂载到 `/app/runtime`。不要用数据目录替代程序卷。新建命名卷自动继承镜像中目录的 UID `10001`；使用宿主机绑定目录时，由部署者设置该目录的属主和写入、执行权限。单独 `docker run` 时也应明确指定命名卷，例如 `-v easyrun_runtime:/app/runtime`，以便后续重建继续使用同一卷。

### 发布发行包

维护者推送稳定标签（例如 `v0.2.0`）触发 `.github/workflows/release.yml`：

| 系统 | 安装包 |
| --- | --- |
| Windows amd64 | `easyrun_v0.2.0_windows_amd64.zip` |
| Linux amd64 | `easyrun_v0.2.0_linux_amd64.tar.gz` |
| Linux arm64 | `easyrun_v0.2.0_linux_arm64.tar.gz` |

各完整发行包根目录包含 `easyrun.exe` 或 `easyrun`，以及通用模型、当前平台推理库和资源说明；都启用 CGO，另附统一的 `checksums.txt`。首次部署解压完整包即可发现模型，在线更新器只提取根目录主程序，保留已部署的配置、密钥与模型。工作流通过全部构建后先创建草稿、上传完整资产再发布，已有 Release 不覆盖。

### 回滚边界与测试

二进制回滚不是数据库时间旅行。发行迁移应向后兼容，安装大版本前仍需备份数据库、主密钥和钱包；若新版本已经执行不兼容迁移，应按发行说明恢复数据库备份。

自动化测试覆盖强更取消/拒绝、缓存过期、重启持久化、调度跳过、权限与公开无凭据下载、校验文件与压缩包拒绝场景、Windows 真实进程替换与失败自动回滚。测试使用临时目录、独立数据库 schema 和模拟发行包，不触碰真实客户或链上资产。

容器回归测试（Linux Docker Engine 与 Python 3，在项目根目录执行）：

```bash
python3 scripts/test-container-update.py
```

脚本构建测试专用版本，在无外网出口的独立网络、新建数据库及命名卷中验证首次启动、在线安装、重建保留版本、协议不兼容拒绝、坏版本回滚和镜像切换。它不读取部署环境文件，不使用线上账号或链上资产；结束时只清理本次随机命名的测试资源。日志及通过后的 `result.json` 保留在 `.local/easyrun-update-test-*`，不会加入发行包。
